# Feature Specification: 用户登录、舱位购买与订单查询

**Feature Branch**: `003-user-booking-order`  
**Created**: 2026年1月9日  
**Status**: Draft  
**Input**: 在该项目的原功能之上，添加用户登录页面（登录/登出，用户信息管理，5个默认用户）、舱位购买功能（船期库存、购买按钮、创建订单、扣减库存）、订单查询功能（按订单号查询、展示订单详情）

## 假设 *(Assumptions)*

- 用户认证采用会话机制，登录状态在浏览器关闭后失效
- 密码以明文形式存储在JSON文件中（仅用于演示目的，生产环境需加密）
- 订单号采用自动生成规则（格式：ORD-YYYYMMDD-XXX），确保唯一性
- 库存扣减为即时操作，不支持并发锁机制（单用户演示场景）
- 订单数据持久化存储在JSON文件中，与其他静态数据保持一致
- 每次购买操作只能购买1个舱位
- 用户只能查询自己创建的订单
- 登录页面为独立页面，未登录用户访问任何功能页面自动重定向到登录页

## Clarifications

### Session 2026-01-09

- Q: 5个默认用户应该来自哪些国家？ → A: 中国、美国、德国、新加坡、日本（覆盖主要航运区域）
- Q: 订单查询页面的导航入口如何设计？ → A: 顶部导航栏新增"我的订单"菜单项
- Q: 点击"购买"按钮后是否需要确认弹窗？ → A: 需要确认弹窗（防止误操作）
- Q: 我的订单列表默认按什么顺序排列？ → A: 按下单时间倒序（最新订单在前）
- Q: 订单列表是否需要分页？如需要，每页多少条？ → A: 需要，每页10条（与船期列表保持一致）

- Q: 登录会话的有效期是多久？ → A: 浏览器会话期间有效（关闭浏览器失效）
- Q: 登录失败的错误提示应展示多长时间？ → A: 持续显示直到用户重新输入
- Q: 库存数量在UI上的展示格式是什么？ → A: "库存: X"格式（简洁明了）

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 用户登录 (Priority: P1)

作为系统用户，我希望能够使用用户名和密码登录系统，以便访问系统的各项功能。

**Why this priority**: 登录是所有功能的前置条件，用户必须登录后才能使用舱位购买和订单查询功能。

**Independent Test**: 用户在登录页面输入正确的用户名和密码，成功登录后跳转到系统主页。

**Acceptance Scenarios**:

1. **Given** 用户未登录, **When** 访问系统任意功能页面, **Then** 自动重定向到登录页面
2. **Given** 用户在登录页面, **When** 输入正确的用户名和密码并点击登录, **Then** 登录成功并跳转到系统主页
3. **Given** 用户在登录页面, **When** 输入错误的用户名或密码并点击登录, **Then** 显示"用户名或密码错误"提示，保持在登录页面
4. **Given** 用户在登录页面, **When** 用户名或密码为空时点击登录, **Then** 显示相应字段的必填提示
5. **Given** 用户已登录, **When** 刷新页面或重新打开浏览器标签页, **Then** 保持登录状态（同一浏览器会话内）

---

### User Story 2 - 用户登出 (Priority: P1)

作为已登录用户，我希望能够安全地退出系统，以保护我的账户安全。

**Why this priority**: 登出功能是用户安全的基本保障，与登录功能配套使用。

**Independent Test**: 已登录用户点击登出按钮，成功退出并返回登录页面。

**Acceptance Scenarios**:

1. **Given** 用户已登录, **When** 点击页面上的"登出"按钮, **Then** 清除登录状态并跳转到登录页面
2. **Given** 用户已登出, **When** 尝试访问需要登录的页面, **Then** 重定向到登录页面

---

### User Story 3 - 查看船期库存 (Priority: P1)

作为已登录用户，我希望在船期查询结果中看到每个船期的可用库存数量，以便决定是否购买。

**Why this priority**: 库存展示是购买功能的前置条件，用户需要知道是否有可购买的舱位。

**Independent Test**: 用户查询船期后，每条船期结果中显示当前库存数量。

**Acceptance Scenarios**:

1. **Given** 用户已登录并在船期查询页面, **When** 查看船期列表, **Then** 每条船期信息中显示当前库存数量
2. **Given** 船期库存大于0, **When** 显示船期信息, **Then** 该船期行显示"购买"按钮
3. **Given** 船期库存等于0, **When** 显示船期信息, **Then** 该船期行显示"暂无库存"文字，不显示购买按钮

---

### User Story 4 - 购买舱位 (Priority: P1)

作为已登录用户，我希望能够购买有库存的船期舱位，系统自动创建订单并扣减库存。

**Why this priority**: 购买功能是核心业务功能，直接产生业务价值。

**Independent Test**: 用户点击购买按钮，系统创建订单、扣减库存，并显示购买成功提示。

**Acceptance Scenarios**:

1. **Given** 用户已登录且船期库存大于0, **When** 点击该船期的"购买"按钮, **Then** 系统创建订单并扣减1个库存
2. **Given** 购买操作成功, **When** 订单创建完成, **Then** 显示"购买成功"提示，包含订单号信息
3. **Given** 购买操作成功, **When** 刷新船期列表, **Then** 该船期的库存数量减少1
4. **Given** 购买前库存为1, **When** 购买成功后, **Then** 该船期显示"暂无库存"替代购买按钮

---

### User Story 5 - 按订单号查询订单 (Priority: P2)

作为已登录用户，我希望能够根据订单号查询我购买过的订单，查看订单详细信息。

**Why this priority**: 订单查询是购买功能的后续保障，让用户能够追溯自己的购买记录。

**Independent Test**: 用户输入订单号进行查询，系统返回匹配的订单详细信息。

**Acceptance Scenarios**:

1. **Given** 用户已登录且有订单记录, **When** 输入正确的订单号并查询, **Then** 显示该订单的完整信息
2. **Given** 用户已登录, **When** 输入不存在的订单号并查询, **Then** 显示"未找到订单"提示
3. **Given** 用户已登录, **When** 输入其他用户的订单号并查询, **Then** 显示"未找到订单"提示（保护隐私）
4. **Given** 订单查询结果显示, **When** 用户查看订单详情, **Then** 展示订单号、下单时间、起运港、目的港、ETD、运输耗时、承运公司等完整信息

---

### User Story 6 - 查看我的订单列表 (Priority: P2)

作为已登录用户，我希望能够查看我所有的订单记录，无需记住每个订单号。

**Why this priority**: 订单列表提供更便捷的订单查询方式，提升用户体验。

**Independent Test**: 用户进入订单查询页面，默认显示当前用户的所有订单列表。

**Acceptance Scenarios**:

1. **Given** 用户已登录且有订单记录, **When** 进入订单查询页面, **Then** 显示当前用户的所有订单列表
2. **Given** 用户已登录但无订单记录, **When** 进入订单查询页面, **Then** 显示"暂无订单记录"提示
3. **Given** 订单列表显示, **When** 用户查看列表, **Then** 每条订单显示订单号、下单时间、起运港、目的港等关键信息

---

### Edge Cases

- 当用户在购买过程中库存被其他操作清零时，应提示"库存不足，购买失败"
- 当订单数据保存失败时，应回滚库存扣减并提示用户重试
- 当用户数据文件损坏或不存在时，应提示系统错误并引导联系管理员
- 当用户连续快速点击购买按钮时，应防止重复下单（按钮防抖或禁用）
- 当登录会话过期时，应自动跳转到登录页面并提示"会话已过期，请重新登录"

## Requirements *(mandatory)*

### Functional Requirements

**用户管理**

- **FR-001**: 系统必须提供用户登录页面，包含用户名和密码输入框及登录按钮，用户名和密码的最大输入长度约束为30
- **FR-002**: 系统必须验证用户登录凭据，验证通过后建立用户会话
- **FR-003**: 系统必须在所有功能页面的顶部区域显示当前登录用户名和"登出"按钮
- **FR-004**: 用户点击"登出"按钮后，系统必须清除会话状态并重定向到登录页面
- **FR-005**: 未登录用户访问任何功能页面时，系统必须自动重定向到登录页面
- **FR-006**: 用户数据必须包含以下字段：用户名（唯一标识）、密码、邮箱、所在国家
- **FR-007**: 系统必须初始化5个默认用户数据，数据以JSON格式存储

**船期库存**

- **FR-008**: 船期数据必须新增库存字段，初始值默认设置为99
- **FR-009**: 船期查询结果列表中必须显示每条船期的当前库存数量
- **FR-010**: 当船期库存大于0时，该船期行必须显示"购买"按钮
- **FR-011**: 当船期库存等于0时，该船期行必须显示"暂无库存"文字，不显示购买按钮

**订单管理**

- **FR-012**: 用户点击"购买"按钮后，系统必须创建订单并扣减该船期1个库存
- **FR-013**: 订单数据必须包含以下字段：订单号、下单用户（用户名）、下单时间、船期编号、起运港、目的港、ETD、运输耗时、承运公司
- **FR-014**: 订单号必须自动生成，格式为"ORD-YYYYMMDD-XXX"，确保唯一性
- **FR-015**: 订单数据必须持久化保存到JSON文件中，保证用户下次登录能查询
- **FR-016**: 购买成功后弹窗显示成功提示，包含生成的订单号
- **FR-017**: 用户点击"购买"按钮后，系统必须弹出确认对话框，用户确认后才执行购买操作
- **FR-018**: 库存变更后，系统必须同步更新船期JSON数据文件以持久化库存数据

**订单查询**

- **FR-019**: 系统必须在顶部导航栏提供"我的订单"入口，作为独立页面
- **FR-020**: 系统必须提供订单查询页面，支持按订单号查询
- **FR-021**: 订单查询必须仅返回当前登录用户的订单，不能查询其他用户的订单
- **FR-022**: 订单查询结果必须展示订单所有字段的数据
- **FR-023**: 系统必须在订单查询页面默认展示当前用户的所有订单列表
- **FR-024**: 订单列表必须按下单时间倒序排列（最新订单在前）
- **FR-025**: 订单列表必须支持分页浏览，每页固定显示10条记录

**用户界面**

- **FR-026**: 登录成功后，系统必须默认跳转到船期查询页面
- **FR-027**: 船期列表中库存数量必须以"库存: X"格式展示
- **FR-028**: 登录失败的错误提示必须持续显示，直到用户修改了用户名或密码
- **FR-029**: 5个默认用户必须分别来自中国、美国、德国、新加坡、日本

### Key Entities

- **用户 (User)**: 表示系统用户，包含用户名（唯一标识）、密码、邮箱、所在国家
- **船期 (Shipping Schedule)**: 表示一条航运船期信息，在原有基础上新增库存字段
- **订单 (Order)**: 表示用户购买舱位的订单记录，包含订单号、下单用户、下单时间、关联的船期信息

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 用户能够在10秒内完成登录流程（输入用户名密码到进入主页）
- **SC-002**: 用户能够在船期列表中直观看到库存状态和购买选项
- **SC-003**: 用户完成一次购买操作的时间不超过5秒（点击购买到看到成功提示）
- **SC-004**: 用户能够在30秒内通过订单号查询到订单详情
- **SC-005**: 系统正确保存所有订单数据，用户下次登录能查询到之前的订单
- **SC-006**: 库存扣减准确无误，购买后库存数量正确减少
- **SC-007**: 首次使用的用户能够成功完成登录、购买、查询订单的完整流程
